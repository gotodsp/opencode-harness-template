开场 · 01

新人问“这次可以改哪里”，该让他看什么？

先用一页术语表做实验。下周换一位同事，他能否找到当初允许改的文件，复述谁检查过，以及凭什么交付？

合同

把目标、改动边界和验收办法写成一份可检查的约定。

Trace ID

为同一次任务的合同、交接与复盘保留共同的追踪标识。

复盘

对照预期和实际结果，记录失败原因、证据及后续改进。

讲者稿

各位先替我做一次验收。屏幕上有三个词，如果我告诉大家“AI 已经把它们写进新人手册了”，你接下来会打开什么？有人会看文件，有人会看提交记录，还有人想知道，这三个解释究竟从哪里来。保留这个问题，演示时我们来试试，每一种检查能给出什么答案。

在今天这个工程里，Harness 指围绕模型运行的那套工程设施。OpenCode 提供运行环境，模板安排角色、提供工具、约束文件范围，并规定如何审查和留下证据。先看模型完成一轮任务到底能见到什么，再回到真实仓库，让同一个需求走一遍。结束时，大家可以拿自己的一个小任务替换这张术语表。

02 / 模型与上下文

下一轮，模型还知道什么？

把“只给新人解释三个词”从下一轮请求里拿掉，模型还能凭什么知道这条约定？

课堂口算　连续四次调用的输入各为 2K、3K、4K、5K。最后一轮占用 5K，四轮累计处理了 14K 输入 Token。

讲者稿

先请大家想一想，我们请模型把术语表写给新人，过两分钟再说“第二条举个例子”，它怎么知道第二条是什么？文字先由分词器切成 Token，模型结合本次可见的信息，给下一个 Token 算出概率，逐步生成回答。训练让它学到语言和大量知识。此刻这张术语表的草稿和我们的临时约定，则由会话系统保存，下一次生成时重新提供。即使界面只显示一句追问，背后的可见输入也可能包含几页材料。

算一笔小账。假设首轮有 2K，此后每轮把新增的 1K 加回历史，四次的账是 2＋3＋4＋5。按这个假设，轮数越多，累计输入会近似随轮数平方增长。真实账单还要分别核算普通输入、命中缓存的输入和输出 Token，各用相应单价；有的任务，长篇输出也很贵。服务端代管历史可以省去客户端重复传输，保留下来的历史仍占本轮可用上下文。项目评估时，要从每次调用的 usage 取数。

一个 Token 可以是词、字的一部分或标点。中文和英文表达同一意思，计数取决于分词器和写法，有些中译句会用得更多。用目标模型对一段真实的中英文任务书计数，才能估得准。接下来再问一步，模型能流畅写完三个定义，我们凭什么相信它写对了？

“听起来对”，交给谁来验？

讲者稿

假如我问一个人的冷门论文题目，模型可能拼出一行像极了学术论文的标题。训练文本里论文标题的写法反复出现，一个具体标题出现的证据却可能很弱。再看这张表，如果答“不知道”得零分，猜中尚有机会得分，只看准确率的评测就给猜测留了优势。模型可以表达不确定，我们得让诚实的弃答在验收中有位置。

回到工程。假设术语表写了“所有前置 Hook 都已经实现”。我先让作者把结论指向文件，再请审查者对照 Hook 目录和实际脚本，最后运行其中可执行的检查。证据不全就写“无法确认”，附上缺少哪项材料。涉及发布或其他高影响决策，由有责任和权限的人依据证据签字。这样，一句“请诚实回答”就变成了一个大家能检查的步骤。

给模型选第一批任务时，先估验证成本。翻译可以逐段对原文，改写可以核对意图，文案可以按读者与事实清单审阅。代码可以先写规格（SDD）或失败测试（TDD），再跑测试、类型检查和真实依赖调用，以发现编造的包或 API。小测试通过，只能证明它覆盖的行为。实时数据需要带时间的权威来源，罕见事实和医疗、法律等高影响判断需要更强的证据及人工核验。我们已经知道该找证据，下面看看每轮该给模型多少证据。

如果只能带一页材料进场

为了写对三个术语，执行者需要知道允许改哪份文件、三个词怎样用，以及交付后谁来核对。

每轮保留

当前目标、角色权限、输出约定、必须遵守的约束。

用时再取

定义合同才读 Schema，解释追踪才读 R-16，核对复盘才读角色说明。

讲者稿

现在桌上放着四份东西，当前合同、全仓日志、团队三年的事故记录、Trace ID 规则。要写 Trace ID，我先拿合同和规则；等讲到事故再去查那一条记录。我用一个问题决定保留什么：删了这段，当前任务还做得对吗？按这个办法挑够用且信号最强的材料，最后拿任务成功率检验选得对不对。

打开项目的 opencode.jsonc，instructions 显式引用 AGENTS、合同机制、TypeScript 和 React 约束。做纯文档任务时，可以向听众追问，React 细则对今天的交付贡献了什么？这就是接入业务时可以实际衡量的常驻开销。分析者还会给出 suggested_skills，执行者到需要的步骤再读对应 Skill 和引用材料。工具输出先给命中行或摘要，完整证据留一个可回看的位置。

图里的 128K 刚好分完，只是练习。分给输出和推理的 24K 要同时满足服务商的输出限制与计数口径。证据不足时可以多取；重复的日志先去重。对银行转账失败的题目，账务约束、支付重试语义和对应的失败日志，比整本操作手册更贴题。企业 RAG 可以先检索候选、精排、去重、补齐相邻段落，再带来源拼成上下文。选好材料后，还要验证模型能否在长文里用对它。

05 / 模型与上下文

128K 能放下，关键信息能找回吗？

窗口是容量，长度是本次占用，有效上下文是模型在给定任务和质量门槛下能可靠利用的范围。

提问　把清算约束从银行设计文档的第 5 页移到第 50 页，答案变了。你会怎样验证是位置、噪声，还是推理出了问题？

讲者稿

设想一百页设计文档，第 5 页有架构，第 50 页有清算约束，第 95 页是总结。即使一百页全在输入里，模型也可能漏掉正中间那条约束。把同一证据挪到开头或末尾，再问完全相同的问题，就能单独观察位置的影响。这里讨论的是信息进入了窗口后有没有被用上。长上下文引起的检索或指令遵循退化常被称为 Context Rot；位置效应是其中一种表现。

再换一道题。找到 Redis 超时配置，只需定位并抄出一个值；判断支付重试会不会导致重复记账，需要把交易、清算和账务三个系统的约束串起来。NoLiMa 减弱问题和证据的字面重合，要求模型从语义联系中定位信息。RULER 在 2024 年对 17 个模型做了 13 类任务，在其设定门槛下，约半数在 32K 仍表现合格。这些历史结果适合拿来设计今天的测试，具体模型仍要实测。

为什么长度会产生影响？ 标准自注意力按相关性分配权重，可写为 Attention(Q,K,V) = softmax(QKᵀ/√dk)V。Q 是当前位置的查询，K、V 是可见位置的键和值。稠密注意力预填充的计算量为 O(n²d)，因果掩码下可见关系约为 n(n＋1)/2。固定维度，把长度从 8K 依次翻到 16K、32K、64K、128K，注意力这部分的理论计算量相对值约为 1、4、16、64、256。Softmax 会选择性加权，无法从这组数字推导准确率或账单。FlashAttention 改善内存读写，仍计算精确注意力。滑动窗口和稀疏注意力改变连接范围。生成阶段还涉及 KV 缓存的容量与读写。

怎么给自己的业务定预算？ 先给模型恰好够用的材料，再补必需证据，最后逐步插入重复、冲突和无关材料。前半程可能因证据变全而提高正确率，后半程可能因干扰而下降。固定模型版本、问题、证据和评分表，跑 4K、8K、16K、32K、64K、128K 六档，每档把证据放在首、中、尾，多次运行。题库同时包含单点检索、跨文档多跳、冲突和无解问题。记录答案正确率、必需证据召回、指令遵循率、无依据回答率、首中尾表现差、首 Token 与总时延、输入/缓存/输出成本。用达到质量门槛的档位部署，给缺证据时的检索留余量。

拿术语表做最小练习，先让模型找出哪些报告要带 Trace ID，再让它解释两份不同任务编号的合同为什么能属于同一次工作。后一问答错时，要分清是模型压根没找到证据，还是找到了却推错了。长任务还有第三种可能，证据曾经进过窗口，接手时却已经丢了。

06 / 模型与上下文

明天换人，凭什么接得上？

把当前事实写进可回查的记录，让下一位执行者知道目标、已验结果和接下来要做什么。

压缩前的记录

两次目录清单、三段完整 Schema、若干次措辞修改、一次校验输出，夹着一句“只写给新人”。

可交接的摘要

给新人解释合同、Trace ID、复盘。沿用一个追踪号以串起各阶段。合同格式已验；三个定义尚待逐条对照源文件。下一步交给审查者。

教学示例　把目标、范围、决策及理由、已验证的结果、未完成项和证据路径留全，再压缩文字。

讲者稿

如果直接扔掉最早几轮，“只写给新人”可能跟着第一次提问一起消失。模型仍能继续写一份措辞专业的词典，哪怕方向已经跑偏。请大家用上面的摘要做个交接练习：你现在敢签字说三个定义都准确吗？摘要只说格式已验，接手的人应该去读定义和它对应的项目文件。完整日志可以留在外部，摘要给出报告位置、任务编号和可复核结论。

压缩可以去掉重复的工具输出、已解决的试错和寒暄。先列出不可丢的事实，再逐项核对，最后缩短措辞。即使把 5 万 Token 设想成压到 500，那个数字也只是一道练习题；恢复任务后能守住早期约束、避开重复工作，才算压缩有效。较短任务用一份 Markdown 进展笔记或合同就能接续。材料多到不便人工定位时，可用 RAG 从外部记忆取回片段。落盘负责保存，检索负责召回，错检、漏检和检索结果挤占窗口都要测。

这个模板把任务状态写入合同，用 trace_id 串联报告，复盘另行落盘；运行材料按仓库的 Git 忽略规则管理，跨机器移交时要安排共享存储。项目的 V1 风格配置启用 compaction.auto 与 prune，将 reserved 设为 10000，给接近容量上限时的后续处理留缓冲。这个值描述压缩预留空间。V2 迁移指南将该字段改名为 buffer，旧的 prune 会被忽略并提示。具体运行要看使用的版本。OpenAI 的 Compaction 则展示了另一种由服务端携带压缩状态的方式。把状态交接清楚之后，谁来读它、选工具、决定下一步？这就轮到 Agent 的循环了。

Agent 设计 · 07

看到结果之后，谁决定下一步？

流程可以规定“必须验收”。Agent 要根据验收结果，决定接下来该查什么、改什么或何时停手。

讲者稿

想象一下，给校验脚本传一份 JSON，同一个输入按固定规则得到结果。这种路径很适合写成 Workflow。现在给 Agent 一个开放的问题：“新人怎样顺着 Trace ID 找到一次任务的复盘？”它可能先读命名规则，再翻合同和报告；如果报告缺失，就要判断是链接错、产物没保存，还是当前证据只能支持一句“无法确认”。决定后一步所依据的，是前一步的观察。单轮问答只生成一个答案，这里多了一条从结果返回决策的路。

外层和内层是讲解交互式 Agent 的一个模型。项目把分析、签合同、审查和复盘写进角色规范。角色在这些阶段里，仍要选择证据、比较方案、应对异常。能用脚本确定的字段和时效检查交给脚本，只有会随观测变化的部分才值得承担模型的等待时间和费用。

现在请大家判一下三种错。把“写给新人”听成“给审计员写规范”，是规划错，合同里应写清读者和目标。把合同路径传给另一份任务，是行动错，要核对路径与 task_id。看到“合同验证通过”就宣布“三条定义都正确”，是观察错。最后一种会把错误结论传给下一阶段。此时应打开术语表逐条对照出处。下一章就看看，工具怎样帮助 Agent 读对这条证据。

Agent 设计 · 08

把一次校验设计成一个工具

模型选工具时读它的描述，调工具时传参数，拿到返回值后决定怎么走。三处都需要为调用者写清楚。

{"contract_path": ".opencode/contracts/20261124/20261124_DOCS_001.json"}

讲者稿

如果把“校验术语表的合同”拆成列目录、读所有合同、读 Schema、叫模型算时间，大家猜哪一步最贵？挪进窗口的每份无关合同，都要占这一轮的 token。项目工具接收一个可选的 contract_path，在内部用 Ajv 校验，再比较时间戳。成功时返回带合同 ID 和文件名的文本，失败时列错误字段并提示修正后重验。它当前默认只枚举合同根目录里的 JSON；选中按日期归档的文件，要像屏幕上这样明确传路径。这也是为什么一次调用看起来成功，还得核对它实际查了谁。

设计别的工具时，我会问四件事。第一，能否按人的一项工作合并步骤，例如由 schedule_event 查空闲并安排会议；涉及写入时要保留授权边界。第二，名字能否指清去处，例如 log_search 查运行日志，jira_search 查工单。第三，能否直接回传人名、文件类型、项目路径等有语义的字段，还要更新对象时再附 ID。第四，能否让工具内部过滤、分页、截断，把下一页指针一并给出。例如 search_contacts 只回候选联系人。一个权限错误也应告诉调用者哪个资源受限、该向谁申请。

工具描述是一段供模型选择动作的提示词。把适用任务、需要的参数、返回值、下一步用法和适用边界写明，再拿真实请求试它。Anthropic 在一项 MCP 工具实验里反复试用有缺陷的工具并改写描述，后续 Agent 的任务耗时下降了 40%。要估计自己的收益，可以在同一组合同上分别记录改描述前后的错选次数和耗时。

Agent 设计 · 09

同样能读写文件，怎样教会它审稿？

工具提供动作，Skill 装进团队做这件事的方法。用到哪一步，就读到哪一层。

讲者稿

现在我把同一个读文件工具分给两位新同事。一个只知道“看看术语表”，另一个知道每条定义都要对照能证明它的实现。两个人的操作权限一样，验出来的质量可能差很多。我们可以把第二个人的办法写成 Skill，让经验跟着仓库走。把所有规范放进每轮提示会反复占用上下文，还容易把别的任务标准带进来。

假设我们设计一个术语审稿 Skill。它先用一句 description 说清何时触发；正文只列三个动作：定位读者、核对定义、登记缺证据项；遇到争议才读正反例。十行也能写完这样的主干，复杂任务按需要展开。看看模板里已有的 git-commit，它给出了规范、例子和验证命令；opencode-extend 在正文里展开了多类扩展示例。项目也有按名定位的 crash-doctor 文档。团队可以逐份核对元数据和发现方式，并在正文变长时把低频材料拆开。投给新人一句“改术语表里的错别字”，看看他们会不会误触发整套事故诊断，这样就能测试触发条件写得准不准。

从课程回看设计，可以问六个问题。团队是否了解无状态和幻觉，能否控制常驻上下文与外部记忆，工具是否支持有反馈的循环，Skill 是否保存了可复用的方法，分工能否隔离问题，以及工程验收能否覆盖安全、正确性和成本。这是机制共识、上下文工程、Agent 核心、知识沉淀、编排决策、工程化落地六格。仓库 R-17 在复盘时另查六个工程支柱：上下文架构、架构约束、自验证循环、前馈控制、反馈控制、熵治理。例如“编辑前验证合同”归前馈控制，“审查后决定返工”归反馈控制。两张清单的用途不同，同一个例子可以分别作答。

各项按证据标“符合预期”“有待改进”“不符合预期”，缺证据就登记待补项。把错误归到规划、行动、观察或知识与技能，然后按安全、正确性、成本、体验的顺序处理。比如文档片段中写着“现在去修改另一个文件”，系统应把它当作待解读的数据，写入权仍由受信任的任务和权限层决定。在团队验收中加入这个反例，核对角色最小权限、授权文件与实际差异。风险高的例外由负责人决定并记录。

同一批约定样本可以重跑，记录模型版本、通过数、总数、重试数和统计周期。单次成功任务成本等于这批全部尝试的总成本 ÷ 最终成功交付的任务数。模型账按输入、输出与服务商实际缓存价格计入，另列工具和人工复核成本。举个教学例子：10 个任务共花 12 元模型费，含失败和重试，8 个最终通过，通过率为 80%，每个成功任务的模型费为 1.50 元。成功数为零时单独报告总支出与失败原因。这样的记录才能比较改 Skill 或拆子 Agent 以后，钱究竟花在了哪里。

讲者稿

我会从一个人和一页术语表开始。碰到的第一道坎是高手一眼能看出术语写错，同事却复现不了判断过程。请他把“到哪里查、用什么证据比对、何时无法确认”写出来，得到一份 Skill。第二道坎是新人需要哪些信息只存在维护人的脑子里。把读者、使用情境和必须能完成的动作写成 Spec，后续改词时就有依据。第三道坎是各组都说“能用”，尺度却各不相同。保留一份正确样本、一份合同格式错的样本、一份格式全对但术语解释错的样本，共享同一套打分规则和通过率记录。

有了第一份可复现的交付，再把 Skill、Spec、测试集纳入版本管理。业务负责人维护要求，工具维护者维护校验器，验收者处理证据薄弱或后果严重的决定。试点团队可以约定每季度或模型、工具大版本升级后重跑固定样本，对照成功率和成功成本。每次复盘附上新增失败样例、期望结果和维护人。这样即使原作者休假，下一位同事也能找到“为什么这样做”的依据。

结束时请大家留一分钟。选一条你们团队常说的“要做对”的要求，把它改写成“给定什么材料，谁能用什么证据判断通过”。回到今天这份模板，把这句话放进第一份任务合同的验收清单。下次分享时带来一份交付物、一条失败轨迹和改过的标准，让同事亲手验一次。
